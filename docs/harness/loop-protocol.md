# Loop 协议

Loop 是一次受控工程循环。每个 Loop 都必须经历 Goal、Plan、Execute、Sense、Decide、Distill 六个阶段。

## 1. Goal

输入目标契约，明确本轮要完成什么、为什么做、允许改什么、禁止改什么、完成标准是什么、验证命令是什么、停止条件是什么。

没有目标契约时，不进入实现。

## 2. Plan

把目标契约拆成小任务。每个任务必须能独立验证、独立提交、独立回滚。

计划至少包含：

- 文件范围。
- 测试策略。
- 验证命令。
- 提交粒度。
- 回滚方式。

## 3. Execute

按计划执行。代码变更必须先写测试，再写实现。文档与配置变更也要有对应检查命令。

执行时不得自行扩大目标契约。需要扩大范围时，停止并生成 `handoff` 决策。

## 4. Sense

收集证据。每轮至少记录：

- 当前 git 状态。
- 修改文件列表。
- 执行过的命令与退出码。
- 测试、构建或检查输出摘要。
- 未解决风险。

大日志和原始数据放在 `.harness/runs/<loop-id>/`，不直接提交。

## 5. Decide

根据目标契约和证据做停止决策。

### pass

满足完成标准，验证命令通过，可以交付。

### continue

方向正确，但证据不足或存在计划内剩余步骤，进入下一轮。

### rollback

失败或风险超出目标契约，撤回本轮改动。

### handoff

需要人判断产品、安全、范围或交付语义，停止自动执行并提交证据。

## 6. Distill

把可复用经验写回仓库。

可沉淀位置：

- `docs/harness/playbooks/**`
- `docs/harness/templates/**`
- `scripts/harness/**`
- `AGENTS.md`
- `docs/superpowers/plans/**`

失败经验优先沉淀，因为它能减少下一轮重复踩坑。

## 角色

### Owner

目标负责人，决定产品边界、验收标准和需要人工判断的问题。

### Planner

把目标契约拆成可执行任务，保证每步可验证。

### Execution Agent

读取计划、写测试、实现、验证并提交。

### Sensors

测试、构建、lint、日志、截图、查询计划、diff 检查和安全扫描。

### Harness

控制面，负责目标契约、范围、证据、停止条件和经验沉淀。
